# Lifecycle backend integration contract

Implemented service integration contract. Existing attempt and catalog APIs remain.
See `challenge-lifecycle-and-badges-implementation.md` for validation and unresolved product/deployment gates; this API contract is not a full acceptance signoff.

Catalog rows add `identity_id`, `edition_id`, `duration_group` (`daily`, `monthly`, `yearly`, `special`), `repeat_policy` (`once_ever`, `annual`, `legacy`), `lifecycle_state` (`active`, `retired`), `available_from`, `available_until`, `retired_at`, `restore_at`, `published_at`, `revision_id`. Existing `points IS NULL` means formula inheritance, integer means absolute override. Specials retain legacy windows/behavior. Existing ladder entries retain legacy repeat exception when the runtime repeat switch is enabled; new explicit repeat policies enforce entitlement. YAML must explicitly name identity to renew across years; reused legacy IDs are aliases, never title-matched.

- `catalog.list_challenges(year=None, tier=None, *, duration_group=None, include_retired=False)` lists startable active definitions (availability checked again at start). `get_challenge(id)` resolves active legacy aliases, including retirement records for history; new integration should test lifecycle_state, never treat presence as start eligibility. `list_challenges(..., include_retired=True)` includes history.
- `lifecycle.calculate_deadline(challenge, start: datetime) -> datetime`: exact UTC anniversary, clamps month/year day; Daily validates positive <=24h. Special keeps configured hours. Use this to preview deadlines. Existing attempts retain persisted `ends_at`.
- `attempts.start_attempt` captures rules, scoring, edition and original deadline; monthly/yearly are concurrent. Confirmation uses captured rules, including retired definitions. Honor complete-work requires selected work at start; optional evidence stays in existing evidence JSON.
- `lifecycle.retire_challenge(challenge_id, *, actor, reason, identity=False, effective_at=None, operation_id=None)` / `restore_challenge(...)` are audited. Future restoration must follow retirement; `cancel_restoration` (also `cancel_restore_challenge`) cancels pending restoration with explicit actor/reason/operation. `materialize_restorations(conn, at=None)` rebuilds due active state during startup/scheduled processing, preserving attempts. Existing `admin_delete_challenge` becomes retirement. No physical deletion of published rows.
- Reviewed catalog writes: `catalog_admin.preview_definition(data)` / `apply_definition(preview, *, actor, reason, operation_id)` include prospective Daily cohort progress/award/bonus effects and preserve earned rosters. Published identities cannot be reassigned; override changes require the scoring workflow. `preview_lifecycle(challenge_id, *, action, identity=False, effective_at=None, reason)` / `apply_lifecycle(...)` add current progress and separately labeled future-boundary forecasts. Forecasts use only already-known clears and never issue early awards. Writer and dependency synchronization run in a rolled-back savepoint for previews, then atomically for revalidated apply.
- Reviewed catalog merges: `catalog_import.parse_yaml(content)` bounds input to 1 MiB; `preview_import({'year': int, 'challenges': [...]})` / `apply_import(preview, *, actor, reason, operation_id)` accept at most 1000 definitions. Omitted fields/entries remain unchanged, including existing overrides/lifecycle history. Override/lifecycle changes require their dedicated workflows. The real writer runs in one rolled-back savepoint for preview, then one atomic revalidated apply. Batch writes suppress intermediate roster publication and publish only final complete sets. `attempts.admin_upsert_challenge(..., conn=conn, publish=False)` is an internal batch helper, not an unreviewed route API. Web imports accept pasted YAML or bounded files under the source `challenges/` directory; apply uses the captured normalized payload and never reopens a file.
- Historical roster repairs: `rosters.preview_repair(roster_id, requirements)` / `apply_repair(preview, *, actor, reason, operation_id)` append immutable replacement versions with `supersedes_roster_id`; never update old requirements or fork a repair chain. Validate year/tier/Daily edition membership, calculate member progress and signed bonus deltas, and reject stale/tampered previews. Empty repaired rosters cannot award. Web forms are under `/lifecycle/rosters`.
- `lifecycle.preview_correction(attempt_id, changes, *, recompute_deadline=False, exception_reason=None)` returns a versioned preview. `apply_correction(preview, *, actor, reason, operation_id)` revalidates and atomically corrects facts, rescoring and recomputing badges. Changes can include status, dates, work/evidence, and classification (`tier`, `duration_group`, `category`); explicit exceptions require reasons. Completion timestamp is separate from confirmation timestamp. Original snapshots never change.
- `scoring.preview_recalculation(policy, scope=None, *, include_open=False, include_overrides=False)` / `apply_recalculation(preview, *, actor, reason, operation_id)` / `revert_operation(operation_id, *, actor, reason, revert_operation_id)` expose audited idempotent scoring operations. Policy supports `base_points`, `multipliers`, and edition `points_override` (explicit null clears). Scope supports `edition_ids`, `identity_ids`, `years`, and date limits with `date_field` (`started_at`/`completed_at`). Global changes exclude overrides by default. `retroactive=False` in scope is future-only. Open-attempt replacement snapshots use the complete challenge-applicable scoped policy and effective corrected tier/duration. Actual applied snapshots include policy ID and explicit revision audit/cutover, retained in the operation result for exact, backward-compatible revert. A reviewed revision applied after an actual scheduled start is not overwritten by delayed scheduler catch-up.
- `badges.duration_badges(discord_id, year=None) -> list[dict]` returns highest earned Daily/Monthly/Yearly in that order (max three); dict includes `duration_group`, `tier`, `glyph`, scope/year and receipt metadata. `badge_history` preserves all tiers/years/revoked history. `sync_user(conn, discord_id)` recomputes receipts in the caller transaction. Daily uses versioned rosters and one bonus/year/tier; long badges never add bonuses. `publish_rosters(conn, *, at=None)` snapshots effective Daily requirements without revoking earned awards. `at` is for internal boundary simulation; preview forecasts are rolled back. Version allocation uses the cohort maximum across prospective and repair rows, while prospective comparison selects non-repair rows.

Lifecycle implementation API details (transaction-local helpers):
- `ensure_catalog_records(conn)` populates identities/editions and appends changed immutable definition revisions; uses `docs/lifecycle-schema.sql`. Does not commit. Call after catalog writes, before roster publication.
- `capture_attempt(conn, attempt_id, challenge)` captures immutable rules/scoring, original start/deadline and edition metadata after INSERT, in caller transaction. A creation event preserves the selected work/focus and original facts. Idempotent; never replaces an existing snapshot. Uses `app.services.scoring` if available (falling back to `app.scoring`).
- `effective_rules(attempt) -> dict` returns joined row overlaid by captured rules then effective completion classification. Keeps attempt `id` and `challenge_id` intact (snapshot definition ID never replaces attempt ID).
- `validate_start(conn, challenge, discord_id, start: datetime)` raises `ValueError`; caller MUST call under `BEGIN IMMEDIATE` and insert/capture before commit. Checks database identity/edition availability, explicit repeats, same-identity open attempts across editions, and exclusive Daily slot. Legacy `allow_reattempt` remains caller responsibility.
- Corrections accept `started_at`, `ends_at`, `actual_completed_at`, `completed_at` (compat alias), `confirmed_at`, `verified_at`, `status`, `param`, `content`, `evidence_json`, `verify_method`, `note`, `tier`, `duration_group`, `category`, `media_filter`. `exception_reason` permits intentional date-order/window exceptions, but not malformed dates or invalid statuses. Naive dates are rejected. Changes retain original edition attribution. Preview includes before/after facts, warnings, dependencies and a database fingerprint; apply rejects concurrent source/dependency changes. A start correction retains deadline unless `recompute_deadline=True`. Preview `impact` includes before/after effective point totals, signed `points_delta`, badge receipts and achievement projections, calculated by running the real synchronizers in a rolled-back savepoint. Apply performs the same synchronization atomically. Explicit tier/duration corrections recalculate the effective completion award under its captured scoring policy without altering original award/start snapshots. For active/scheduled attempts, eventual award creation resolves the corrected classification under the accepted scoring policy and absolute override, retaining original accepted snapshots. Receipt metadata links the classification correction's actor, reason and operation ID; first issuance uses the corrected entitlement rather than creating a fictitious prior award.
- `capture_attempt` invokes `scoring.capture_snapshot(conn, challenge, at=attempt.started_at)`; scheduled activation may refresh the accepted scoring snapshot under the actual-start cutover policy, while recording its originally advertised scoring snapshot separately. Lifecycle never rewrites captured deadline/rules.
- Retirement/restoration also append established `challenge_changes` entries and publish prospective Daily rosters; identity-level state remains separate from edition state (roster publishing must consult permanent identity state too). Both retirement and restoration support `effective_at`, with explicit restoration cancellation and no premature reopening. `catalog.availability_sql(alias, at=None)` supplies the shared bound-instant filter for catalog listings and Daily/category progress denominators; scheduled retirement cannot remove a requirement before the boundary. Arbitrary multiple disjoint scheduled interval editing remains a separate missing workflow.

Schema: `challenge_identities`, `challenge_editions`, `definition_revisions`, `lifecycle_events`; additive attempt `identity_id`, `edition_id`, `edition_year`, `definition_revision_id`, `rules_snapshot_json`, `scoring_snapshot_json`, `original_deadline`, `original_started_at`, `scheduled_start_original`, `created_at`, `confirmed_at`, `verified_at`, `actual_completed_at`, `original_completion_json`, `effective_completion_json`, `correction_revision`, `provenance`, `calendar_timezone`, `calculation_version`; `attempt_events`; `scoring_policies`, `award_ledger`, `point_adjustments`, `admin_operations`; `daily_rosters`, `badge_receipts`, `badge_events`.

Ledger helpers (transaction-local): `scoring.ensure_completion_award(conn, attempt_id)` adds/reconciles a completed source; `scoring.set_award(conn, source_key, points, *, operation_id, actor, reason)` appends signed adjustments; `scoring.sync_user(conn, discord_id, *, actor='system', reason=None, operation_id=None)` ensures legacy direct inserts are baselined and voids reconcile. Completion helpers accept the same audit context. Administrative corrections propagate their actor/reason/operation to signed adjustments; a combined reinstatement/reclassification uses `<operation_id>:reinstate` for the intermediate restoration and the parent ID for the final classification adjustment. Original completion/bonus points are retained; mutable effective_points is the rebuildable projection. `scoring.user_points(conn, discord_id)` is authoritative. Migration labels inferred historical points as `legacy_baseline`, preserves known dates and does not invent actual completion dates. No live DB is touched during implementation/tests.

Discord catalog/void operations collect a human reason, return an owner-bound private JSON preview attachment, recheck current admin authorization on apply and use stable operation IDs. Backend previews are revalidated before writes. Owner content/focus/match corrections preserve original completion facts, append before/after `attempt_events`, increment correction revisions and clear stale evidence caches; identical retries are no-ops. Completion confirmation retains subsecond precision to remain ordered after a subsecond start. `admin_test_verify` is now diagnostic-only: `apply=True` is rejected. Diagnostic confirmation does not activate/expire attempts or persist match fixups; direct forced/synthetic writes through `confirm_attempt` are blocked. `admin_completion.preview_attestation(attempt_id, *, discord_id, actual_completed_at, actor, reason, content=None, exception_reason=None)` requires a nonfuture, timezone-aware actual completion and the selected member's active/expired/abandoned attempt, preserves existing evidence and returns an ordinary correction preview. Discord modal and apply recheck owner/current admin role. Applying records administrative attestation separately from synthetic proof, with no automatic public announcement or external reward. Existing historical synthetic receipts remain intact. Broader independent admin correctness/security and actual UI acceptance remain release gates.

Renderer integration (complete): `render_userinfo_card(..., duration_badges=badges.duration_badges(discord_id, year))` accepts the backend row list directly. It hides unearned slots and displays max three 日/月/年. Existing `cleared_tiers` remains Daily-only styling. Card renderer no longer needs font work; 42 rendering tests pass on Mac.

Tadoku/progress integration: `IncompleteLogsError` is raised instead of returning partial evidence at pagination limits/HTTP failures/bad timestamps. Generic existing fetch error handling remains compatible. Long-window requests use user-wide logs, never a single contest fallback. Progress failure clears cached goal_ok and displays evidence incomplete. Milestone state preserves delivered markers across deadline revisions, with effective_window/deadline_revision tracking.
